# 统一比赛数据与自定义策略能力建设

本文定义自定义策略所需的统一比赛数据：为什么采集、保存什么格式、如何从数据形成可复用的新能力。采集器实现位于 `agent/match-data-recorder` 分支；本文作为策略设计说明保存在 `main`，不表示这些模型已经接入正式策略。

## 1. 采集目的

一场 3v3 比赛中的球动力学、机器人运动、抢球、传球、射门和门将决策共享同一条时间轴。统一采集的目标是一次保存公开接口允许获得的原始事实，之后针对不同能力离线切片、清洗、拟合和回放，而不是为每一种模型反复修改 Agent、重复运行比赛。

采集遵循以下原则：

- 只记录 Agent 已经可以看到的比赛状态、自身状态和实际执行命令。
- 不使用仿真器内部摩擦系数、接触冲量、隐藏碰撞标签或非公开控制接口。
- 记录器只观察，不改变角色分配、移动、踢球和规则判断。
- 原始 JSONL 永久保留；清洗标签、特征和模型参数另行生成，保证结果可复现。
- 学习模型只能改善战术判断，不能绕过 GameController、处罚、重启距离等硬规则。

## 2. 数据文件格式

统一输出为 JSON Lines 文件，每行是一个独立 JSON 对象：

```text
match_dataset.team<N>.jsonl
```

每行都包含：

```json
{"schema_version":2,"record_type":"frame"}
```

`schema_version` 用于兼容后续字段升级，`record_type` 决定该行的具体结构。

### 2.1 `metadata`

每次 Agent 进程启动时写入一次，描述本次数据的固定背景：

- 我方和对方 team ID；
- 机器人 ID、名称与 READY 固定槽位；
- 控制循环频率和世界帧采样频率；
- 场地长度、宽度、球门和禁区尺寸；
- 本场使用的全部策略参数；
- 世界帧和踢球轨迹的采样说明。

模型训练必须关联对应的 `metadata`，不能把不同场地、策略参数或仿真版本的数据无条件混合。

### 2.2 `frame`

以 10 Hz 保存全场最新快照。主要字段如下：

| 字段 | 内容 | 主要用途 |
| --- | --- | --- |
| `frame_id`、`monotonic_sec`、`elapsed_sec` | 帧编号和单调时间 | 对齐全部轨迹与事件 |
| `game` | 比赛阶段、set play、开球队伍、剩余时间、比分、处罚 | 状态机、规则审计、结果标注 |
| `ball` | 球位置、置信度、观测时间和数据年龄 | 球速、减速度、停球点和威胁预测 |
| `teammates` | 全部队友位姿、朝向和观测年龄 | 运动模型、角色协作、空间控制 |
| `opponents` | 全部对手位姿、朝向和观测年龄 | 拦截、传球线路和危险度判断 |
| `commands` | 实际执行的移动、踢球、停止或 no-op 命令及原因 | 指令到运动响应、决策回放 |
| `roles` | 每名我方机器人的动态角色 | 角色切换稳定性和团队结构评估 |
| `robot_statuses` | 模式、跌倒状态、可恢复性及更新时间 | 可达性修正、可靠性和安全分析 |

世界帧采用 10 Hz，是在运动分析精度、磁盘体积和控制循环开销之间的折中。它不取代控制循环，也不降低策略本身的运行频率。

### 2.3 `kick`

每次自身命令从非踢球切换到 `KickIntent` 时开始一个踢球样本。它记录：

- 踢球队员和动态命令原因；
- 踢球方向、力度以及球在机器人坐标系下的位置；
- 踢球瞬间的机器人位姿和裁判上下文；
- 控制循环看到的每一个新球观测，而不是降采样到 10 Hz；
- 轨迹结束原因，例如停球、球数据过期、下一次踢球、超时或 Agent 关闭。

高频球轨迹用于估计初速度和滚动衰减。机器人碰撞、门柱、边界和裁判重置造成的轨迹变化需要在离线阶段标记，不能直接当作自由滚动样本。

### 2.4 `session_end`

正常关闭时写入：

- 本次运行总时长；
- 世界帧总数；
- 完成的踢球样本数。

缺少 `session_end` 通常表示进程被强制结束或容器被直接销毁；数据仍可分析，但必须先检查文件末尾是否为完整 JSON 行。

## 3. 从原始数据形成新能力

新能力采用统一流程：原始数据质量检查，自动分段与干扰标注，训练集和验证集划分，建立简单基线，离线回放比较，最后才小范围接入 `tactics/` 或 `play/`。

| 新能力 | 使用的数据 | 第一版模型 | 策略强化方式 | 核心评价指标 |
| --- | --- | --- | --- | --- |
| 球速与停球点预测 | 高频球轨迹、踢球力度/方向、周围机器人 | 滑动窗口速度 + 分段恒减速 | 追未来落点而非当前球位 | 停球点误差、停止时间误差 |
| 机器人到达时间 ETA | 位姿、朝向、`vx/vy/vyaw`、障碍和运行状态 | 转向延迟 + 启动/巡航/制动模型 | 选择真正最早到达的机器人 | 到达时间误差 |
| 动态拦截与 Chaser 选择 | 球预测、双方 ETA、角色 | 沿球轨迹搜索最早可达交点 | 输出拦截点和抢球时间优势 | 抢球成功率、无效换人次数 |
| 控球权判断 | 球与机器人距离、轨迹突变、踢球事件 | 我方/对方/争抢/自由球概率 | 驱动压上、回防和攻防切换 | 球权判断准确率和稳定性 |
| 动态避障 | 双方轨迹、自身命令、跌倒和处罚 | 常速度最近会遇距离 | 提前绕开未来碰撞点 | 碰撞率、跌倒率、绕行时间 |
| 传球选择 | 踢球事件、接球队友 ETA、对手 ETA、线路净空 | 传球成功概率与候选点评分 | 选择有时间优势的接球点和力度 | 传球成功率、向前收益 |
| 射门威胁 | 射门距离/角度、门将位置、线路、球轨迹和比分 | 简化进球概率评分 | 在射门、传球和带球之间比较收益 | 进球率、射正率、被封堵率 |
| 门将防守 | 朝己方球门的球轨迹、门将 ETA、对手位置 | 门线交点与到达时间预测 | 留守、横移或出击的动态选择 | 失球率、有效拦截率、错误出击率 |
| 接应与空间控制 | 全部位置、球权、传球线路和下一步威胁 | 候选空间点评分 | Supporter 主动拉开并保护丢球后区域 | 可用传球线路、队友间距、二点球优势 |
| 角色分配迟滞 | 每帧角色、ETA、球权和后续结果 | 切换收益减去切换成本 | 只有新角色具有明确优势时换人 | 切换频率、切换后收益 |
| 攻防状态机 | 球权、球场区域、比分、剩余时间和角色 | 可解释的离散状态机 | 不同阶段切换进攻和防守权重 | 失球前暴露率、进攻推进效率 |
| 规则与可靠性 | GameController、处罚、命令、位置、数据年龄和跌倒 | 硬约束检查与故障统计 | 在最终命令前阻止违法或不安全行为 | 处罚率、违规命令数、数据过期率 |

## 4. 优先落地顺序

第一阶段建立两个所有战术共享的基础模型：

1. 球轨迹、减速度和停球点；
2. 机器人转向、移动与到达时间 ETA。

第二阶段用它们组合出直接影响比赛的能力：

3. 动态拦截点与 Chaser 选择；
4. 门线威胁与门将拦截；
5. 控球权判断；
6. 传球和射门候选评分。

第三阶段再优化团队协作：

7. 动态避障；
8. Supporter 空间选择；
9. 角色切换迟滞；
10. 攻防状态机。

规则安全层始终作为硬约束并行保留，不依赖训练数据决定是否执行。

## 5. 数据质量与覆盖率

一场完整比赛足以验证采集链路并建立第一版基线，但不保证覆盖不同力度、方向、碰撞、任意球、比分和对手风格。首次收到数据后应先生成覆盖率报告，至少检查：

- 文件和 JSON 行是否完整，是否正常写入 `session_end`；
- 实际帧率、时间戳是否单调、观测是否过期；
- 踢球数量、方向、力度和自由滚动距离分布；
- 移动距离、朝向差、指令速度和到达行为分布；
- 双方接近、碰撞、跌倒、处罚和角色切换次数；
- 射门、传球、重启、领先和落后局面的覆盖情况。

只有覆盖不足时才补跑有针对性的仿真；不预先为每种模型拆分采集分支。

## 6. 代码落点约定

- 纯预测、评分、几何和物理模型放入 `src/tactics/`。
- 角色分配、攻防流程和何时调用能力放入 `src/play/`。
- GameController、处罚、停止和硬件安全继续由行为树安全层兜底。
- 原始采集与离线分析工具不得成为正式比赛决策的外部依赖。

模型进入默认策略前，必须同时保留旧基线，完成离线回放比较，并支持通过配置快速关闭新能力。
