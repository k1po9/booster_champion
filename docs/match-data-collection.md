# 3v3 竞争能力与统一比赛数据采集

本分支使用一个只读的比赛记录器，在默认策略正常比赛时并行采集多类模型所需数据。记录器不移动球、不重置仿真、不制造开球，也不修改任何下发给机器人的命令。

## 为什么采一份统一数据

不同能力并不是互相独立的。例如，判断一次传球是否成功，需要同时知道球轨迹、队友和对手轨迹、踢球指令、角色分配以及裁判状态。因此应先保存同一时间轴上的原始可观测量，再离线生成速度、加速度、控球权、拦截点等派生特征。

| 竞争能力 | 后续可拟合或评估的模型 | 本次保存的原始数据 |
| --- | --- | --- |
| 球速、减速度、停球点 | 分段恒减速、速度相关阻力或数据驱动回归 | 踢球方向/力度/触球相对位置、高频球轨迹、置信度 |
| 机器人可达时间 | 转向延迟 + 加速/巡航/制动模型，或经验 ETA 回归 | 自身位姿、实际下发的 `vx/vy/vyaw`、模式和跌倒状态 |
| 抢球与拦截 | 球预测轨迹与双方机器人 ETA 的时空交点 | 球、全部队友/对手位姿、指令和角色 |
| 动态避障 | 常速度短时预测、最近会遇距离和通行成功率 | 全部机器人轨迹、自身运动指令、跌倒/处罚结果 |
| 角色分配稳定性 | 分配代价、迟滞、切换次数及切换后的收益 | 每帧角色、球和机器人状态、命令原因、比分 |
| 传球与射门选择 | 传球成功概率、射门威胁、门线穿越概率 | 踢球事件、双方位置、球轨迹、比分和比赛阶段 |
| 门将防守 | 到达门线时间、威胁球分类、扑救覆盖 | 球预测所需轨迹、门将/对手位置和下发指令 |
| 规则与可靠性 | 状态机合规、处罚率、数据新鲜度和故障恢复 | 完整裁判状态、处罚、观测时间戳、模式和跌倒状态 |

仿真器内部摩擦系数、接触冲量和碰撞标签不是 Agent 的公开输入，所以不会伪造成“真值”。后续会从轨迹反推物理参数，并用机器人距离、边界、门柱和裁判跳变给受干扰样本打标签。

## 输出文件

Agent 启动后，终端会出现：

```text
Match dataset path: /tmp/booster_agent/soccer_logs/<run-id>/match_dataset.team<N>.jsonl
```

整个进程只写这一个 JSONL 文件。每行都有 `schema_version=2` 和以下一种 `record_type`：

- `metadata`：队伍、机器人名、场地尺寸、策略参数和采样频率。
- `frame`：10 Hz 全场快照，包含裁判/比分/处罚、球、双方机器人、实际执行命令、动态角色和自身运行状态。
- `kick`：每次自身 `KickIntent` 对应的高频去重球轨迹。轨迹持续到停球、数据过期、下一次踢球、八秒上限或 Agent 关闭。
- `session_end`：本次运行时长、帧数和完成的踢球样本数。

世界帧限制为 10 Hz，是为了让运动、角色和交互分析有足够时间分辨率，同时避免 30 Hz 重复快照持续占用控制循环和磁盘。踢球阶段仍保留控制循环见到的每个新球观测，用于拟合初速度和减速度。

## 一次完整采集怎么跑

1. 使用 `agent/kick-data-recorder` 分支构建并启动 Agent。
2. 让默认策略完成一场正常 3v3 仿真比赛；不要通过非公开接口移动球或机器人。
3. 正常停止 Agent，使文件写入 `session_end` 并关闭。
4. 将终端打印路径下的 `match_dataset.team<N>.jsonl` 整个复制出来。
5. 同时说明对手策略、仿真版本，以及本场是否出现手工暂停或重置。

一场数据足以验证采集链路并建立第一版模型，但不保证覆盖各种力度、方向、碰撞、比分和重启局面。第一轮分析会先检查覆盖率和数据质量，再决定是否需要补跑；不会预先拆成多个采集分支。

## 第一轮离线分析顺序

1. 校验时间戳、丢帧率、坐标范围和比赛阶段覆盖率。
2. 识别每次踢球后的无碰撞区间，拟合并留出验证球动力学模型。
3. 用移动命令与位姿响应拟合机器人速度、转向延迟和到达时间。
4. 在两类模型基础上计算拦截点、控球权、传球窗口和门线威胁。
5. 回放角色切换、避障、处罚与失球前后的决策，给策略能力评分。

原始 JSONL 应保留不改；清洗标签、特征表和模型参数另行生成，保证分析可以复现。
