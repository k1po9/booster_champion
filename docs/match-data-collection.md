# 3v3 竞争能力与统一比赛数据采集

本分支使用一个只读的比赛记录器，在默认策略正常比赛时并行采集多类模型所需数据。记录器不移动球、不重置仿真、不制造开球，也不修改任何下发给机器人的命令。

## 为什么采一份统一数据

不同能力并不是互相独立的。例如，判断一次传球是否成功，需要同时知道球轨迹、队友和对手轨迹、踢球指令、角色分配以及裁判状态。因此应先保存同一时间轴上的原始可观测量，再离线生成速度、加速度、控球权、拦截点等派生特征。

| 竞争能力 | 后续可拟合或评估的模型 | 本次保存的原始数据 |
| --- | --- | --- |
| 球速、减速度、停球点 | 分段恒减速、速度相关阻力或数据驱动回归 | 踢球方向/力度/触球相对位置、高频球轨迹、置信度 |
| 机器人可达时间 | 转向延迟 + 加速/巡航/制动模型，或经验 ETA 回归 | 自身位姿、实际下发的 `vx/vy/vyaw`、模式和跌倒状态 |
| 抢球与拦截 | 球预测轨迹与双方机器人 ETA 的时空交点 | 球、全部队友/对手位姿、指令和角色 |
| 动态避障 | 常速度短时预测、最近会遇距离和通行成功率 | 全部机器人轨迹、自身运动指令、跌倒/处罚结果 |
| 角色分配稳定性 | 分配代价、迟滞、切换次数及切换后的收益 | 每帧角色、球和机器人状态、命令原因、比分 |
| 传球与射门选择 | 传球成功概率、射门威胁、门线穿越概率 | 踢球事件、双方位置、球轨迹、比分和比赛阶段 |
| 门将防守 | 到达门线时间、威胁球分类、扑救覆盖 | 球预测所需轨迹、门将/对手位置和下发指令 |
| 规则与可靠性 | 状态机合规、处罚率、数据新鲜度和故障恢复 | 完整裁判状态、处罚、观测时间戳、模式和跌倒状态 |

仿真器内部摩擦系数、接触冲量和碰撞标签不是 Agent 的公开输入，所以不会伪造成“真值”。后续会从轨迹反推物理参数，并用机器人距离、边界、门柱和裁判跳变给受干扰样本打标签。

## 输出文件

Agent 启动后，终端会出现：

```text
Match dataset path: /tmp/booster_agent/soccer_logs/<run-id>/match_dataset.team<N>.jsonl
```

整个进程只写这一个 JSONL 文件。新版每行都有 `schema_version=4`，主要记录类型如下：

- `metadata`：队伍、机器人名、场地尺寸、球半径假设、策略参数和采样说明。
- `frame`：10 Hz 全场快照，包含裁判/比分/处罚、球、双方机器人、实际执行命令、动态角色和自身运行状态。
- `ball_motion`：不限于己方踢球；检测到任意球运动后，保存控制循环看到的每个新球观测、发起事件、交互候选、终止事件和自由路径有效时域，直到自然停球候选、边界、裁判事件、数据过期或超时。
- `kick`：每次自身 `KickIntent` 的命令参数与球轨迹，并通过 `motion_ids` 关联一个或多个 `ball_motion`。
- `robot_eta`：有明确导航目标时的高频自身位姿序列，保存原始目标、避障后的控制目标、到达阈值、转向/奔跑/对齐/到达阶段和实际执行速度。
- `game_event`：GameControl 状态、定位球、停止、发球权或比分变化。
- `ball_motion_label`：裁判事件晚于几何越界时，以追加记录把最近球段关联到进球或定位球等官方标签；关联方法和延迟会原样保存。
- `match_end`：首次收到官方 `FINISHED` 时立即持久化的比赛完成检查点，即使随后直接关闭仿真也可判断比赛数据完整性。
- `session_end`：Agent 正常关闭并排空写队列后的运行时长及各类完成样本计数。

世界帧保持 10 Hz，以控制体积；球运动和 ETA 位姿只在官方 topic 出现新时间戳时去重保存，最高跟随 30 Hz 控制循环。每个控制周期只做常数次距离、边界和状态比较，不做训练、拟合或磁盘扫描。

JSON 编码和磁盘写入由 Python 标准库后台线程串行处理，控制线程只入队；Agent 关闭时排空队列后再关闭文件。加入有限档位后的3000个本地高负载周期参考结果为：平均 0.37 ms、P99 2.91 ms、最大 17.87 ms，低于30 Hz的33.3 ms周期预算。事件分类在后台写线程中对最多12秒的有界轨迹执行，不占用控制线程；该数字仍需在目标仿真复测。

## 标签等级：真值与候选必须分开

公开 API 没有仿真接触冲量、最后触球队员或门柱碰撞事件，因此 schema v4 不会把距离推断伪装成官方真值：

| 等级 | 来源 | 可直接表达的状态 |
| --- | --- | --- |
| 官方确认 | GameControl | 比分变化、比赛状态、`stopped`、定位球、发球权、处罚 |
| 规则几何 | 官方场地尺寸 + 球位姿 | 整球是否越过边线/门线、是否位于门宽内、距门柱中心距离 |
| 观测候选 | 球与双方机器人位姿 | 机器人接触候选、门柱接近候选、方向或速度突变候选 |
| 控制内部事实 | 实际执行命令 | 己方踢球开始、导航原始目标、避障目标、命令阶段 |

`free_roll_terminal_candidate=true` 只会出现在“自然停止候选”且没有接触、越界、门柱接近、方向突变或低置信度标志的球段。它仍是高质量候选而非物理引擎真值；离线清洗必须保留原始 `quality_flags` 和追加的官方标签。

## 球模型所需证据

球能力的主要样本单位不是“必须自然滚到静止”，而是：`突发加速候选 → 前几个球样本 → 后续实际轨迹 → 首个交互或终止事件`。突发加速在排除裁判摆球、边界/门柱反弹和观测跳变后，可结合最近机器人距离标为踢球候选；由于公开 API 没有接触真值，仍保留候选等级。

训练必须拆成两层：

1. **自由路径层**：仅根据加速后的早期球样本预测无人干预时的多时刻位置。截获、二次触球、越界、门框碰撞和异常跳变之后的损失必须屏蔽；事件之前的轨迹前缀仍是有效监督。
2. **场景事件层**：使用完整实际轨迹、球员位置、边界和门框证据，判断自由路径何时会被截断以及终止类型。它可以服务传球成功率、拦截点和出界判断，但不能反向污染球的摩擦/减速参数。

因此自然停止只是长程减速和最终落点的高价值标定样本，不是所有训练样本的准入条件。被截获、出界、碰门框和异常停止都应保留为完整事件样本，并为自由路径层提供事件前的可用前缀。

每条 `ball_motion` 的训练语义字段：

- `launch_event`：加速起点、己方踢球命令或机器人/门柱发起候选，以及速度和距离证据；
- `event_candidates`：后续机器人截获/接触、机器人附近二次加速、门柱接触和无归属运动突变的时刻、证据及置信度；
- `terminal_event`：自然停止、越界、官方状态、观测丢失或超时；
- `free_path_valid_until_sec`：首个高置信交互或终止事件的绝对段内时刻；
- `free_path_horizon_sec`：从加速起点开始可用于自由路径监督的时长；
- `free_path_conservative_*`：连低置信候选也截断的保守版本；
- `ball_motion_label`：晚到的官方比分/定位球覆盖几何候选，优先级固定为“官方 > 几何 > 候选”。

每个高频球点都保存：位置与观测时间、最近队友/对手及距离、整球边界余量、是否越线、是否处于门宽、最近门柱中心距离、GameControl 轻量标记。这样可以：

1. 用官方比分或定位球事件确认进球/出界结果；
2. 在事件广播有延迟时保留越线前的有效自由滚动前缀；
3. 将近机器人、近门柱和明显变向样本作为截断样本，而不是错误的自然停止；
4. 同时采集对方踢出的自由球，不再局限于己方 `KickIntent`。

## ETA 所需证据

仅凭 `vx/vyaw` 无法恢复“要去哪里”。运动控制器现在在不改变硬件命令的前提下，给 `RobotCommand` 附加只读 `motion_target`：

- `requested_target`：策略真正指定的场上目标；
- `control_target`：绕障后本周期实际追踪的目标；
- `arrive_distance`：本次到达阈值；
- `phase`：`turn/run/align/arrived/hold`；
- `avoidance_applied`：是否使用绕障目标。

`robot_eta` 从目标出现时开始，记录起始位姿和朝向，直到到达或被目标变化、踢球、暂停、处罚、跌倒、数据缺失、超时等原因截断。`arrived=true` 是完整 ETA 标签；其他记录带 `censored=true`，可训练启动/转向/局部速度，但不能当作完整到达时间。

## 有限探索档位

采集分支采用确定性轮转，不使用逐帧随机数：

- 踢球力度：`1.00 / 1.25 / 1.50 / 1.75 / 2.00`；
- 线速度上限：`0.40 / 0.60 / 0.80 m/s`；
- 角速度上限保持策略默认 `1.0 rad/s`，避免同时改变线速度和角速度而难以归因；
- 同一次踢球保持同一力度；同一 ETA 目标段保持同一速度上限；只有新踢球或目标发生实质变化时才轮转；
- 选中的线速度上限同时写入 `motion_target.linear_speed_limit_mps` 和每个 ETA 点；实际 `vx/vyaw` 继续原样记录。

档位位于官方踢球接口 `[1.0, 10.0]` 范围的低端，并受当前场地尺度约束，不采集明显会持续制造界外球的高功率。每轮数据验收按档位统计有效事件前球路径窗口和完整ETA到达数；某档有效样本不足时定向补齐，不扩大随机范围。

## 一次完整采集怎么跑

1. 使用 `agent/match-data-recorder` 分支构建并启动 Agent。
2. 让默认策略完成一场正常 3v3 仿真比赛；不要通过非公开接口移动球或机器人。
3. 正常停止 Agent，使文件写入 `session_end` 并关闭。
4. 将终端打印路径下的 `match_dataset.team<N>.jsonl` 整个复制出来。
5. 同时说明对手策略、仿真版本，以及本场是否出现手工暂停或重置。

一场数据足以验证采集链路并建立第一版模型，但不保证覆盖各种力度、方向、碰撞、比分和重启局面。第一轮分析会先检查覆盖率和数据质量，再决定是否需要补跑；不会预先拆成多个采集分支。

## 第一轮离线分析顺序

1. 校验时间戳、丢帧率、坐标范围和比赛阶段覆盖率。
2. 识别每次踢球后的无碰撞区间，拟合并留出验证球动力学模型。
3. 用移动命令与位姿响应拟合机器人速度、转向延迟和到达时间。
4. 在两类模型基础上计算拦截点、控球权、传球窗口和门线威胁。
5. 回放角色切换、避障、处罚与失球前后的决策，给策略能力评分。

原始 JSONL 应保留不改；清洗标签、特征表和模型参数另行生成，保证分析可以复现。
